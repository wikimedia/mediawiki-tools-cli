# Documentation publishing

[Read the guides](index.md). Markdown guides live in `guides/`, grouped by command area (for example `guides/dev/` and `guides/gitlab/`); `wiki.json` maps each source to its MediaWiki.org title. The command reference comes from Cobra help. Both are built from the release checkout and published together after a release. Existing `Cli/` URLs remain stable during the rebrand; the reference index follows the default executable name.

## Build and review

Install [mise](https://mise.jdx.dev/getting-started.html) and Go, then run:

```sh
mise trust
mise install
make docs
make docs-check
make docs-audit
```

Pandoc is pinned in `mise.toml`. The Make targets use `mise exec`, so shell activation is optional.

`_docs/` contains Markdown, converted wikitext and `pages.json`. `docs-check` reads every managed wiki page and finds its last automatic publication. It reports just the changes made on the wiki since that revision, such as spelling fixes; new release changes are kept out of these diffs. Identical reverts do not count as content changes. For guides not automatically published yet, the imported/reviewed revision is the baseline.

`_docs/wiki/report.md` lists these wiki edits with small `.wiki.diff` files and links to the exact wiki revision comparison. `publish-report.md` separately shows the full proposed release changes in `.publish.diff` files. The directory also contains downloaded content and revision snapshots; it is regenerated by each check. CI keeps it as a documentation job artifact. Checking does not need credentials or edit the wiki.

Published pages carry a content fingerprint. If someone edits a page on the wiki, the next publish stops before making any edits. For the initial migration, only reference content verified against the known legacy bot’s publication is adopted automatically (including identical human reverts); imported guides have explicit revision/content baselines in `wiki.json`.

## Find pages left behind

`make docs-audit` lists existing `Cli/` subpages absent from the current build in `_docs/wiki/audit.md`. It separates retirement candidates (`OBSOLETE`, or `OBSOLETE-EDITED` when corrected on the wiki) from retained translations, supported aliases, hidden commands and community pages. Review obsolete pages for redirects, adoption or manual retirement; an absent mapping is not permission to delete a community page.

Moving a Markdown file and updating its `source` in `wiki.json` preserves the wiki URL. Changing a mapped `title` creates or updates the new page; publishing never moves or deletes the old page. Keep useful old URLs as explicitly managed redirects, as the `docker` command reference does, or handle the wiki move manually after reviewing history and incoming links. The audit is read-only and needs no credentials. The `Cli` homepage and its translations remain wiki-managed: edit the Translate source page to update their branding, preserving translation unit markers.

## Bring wiki corrections into Git

```sh
make docs-pull
```

This saves Markdown proposals for guides alongside the wikitext and diffs. It does not modify tracked sources. Merge relevant guide corrections into `docs/`, or update the command help for reference corrections. Check the conversion: wiki templates and other wiki-specific markup may need manual adjustment.

After reviewing a flagged page, acknowledge the exact downloaded content:

```sh
make docs-accept page="Cli/ref/mw_docker"
```

Commit the source fixes and updated `wiki.json`. Acceptance is tied to that snapshot; a later wiki edit is flagged again. Re-run `make docs-check` before tagging a release.

## Add or import a guide

For a new guide, add Markdown under `guides/`, a `source`/`title` entry in `wiki.json`, and a link in `index.md`. Relative Markdown links between mapped guides are converted to wiki URLs. Broken guide links fail the build. Mapped guides are also bundled for offline reading under `mw help guides`, following their folder paths; `index.md` provides the parent topic. Use `--web` to open the mapped wiki page. Keep command help short and point to a guide for longer workflows.

To adopt an existing wiki page:

```sh
make docs-import page="Cli/guide/Gitlab" file="guides/gitlab/index.md"
```

This imports the current revision into Markdown, adds its mapping and records its baseline and attribution. Importing over an existing source saves a `.bak` copy first. Review the conversion and commit the imported files. Unmapped community pages are never published, deleted or renamed by this tool.

## Publish

Set `DOCS_UPDATE_USER` and `DOCS_UPDATE_PASS` to the wiki publishing account and bot password, then run:

```sh
make VERSION=vX.Y.Z docs-publish
```

The release job uses the existing CI secrets. Credentials are read from the environment. Publishing repeats the drift check and sends the inspected revision ID with every edit; a concurrent wiki edit, deletion or creation causes an API conflict instead of an overwrite. There is no force-publish bypass. A conflict during publishing can leave earlier pages updated; correct it and rerun to finish.

The guides are available under [CC BY-SA 4.0](https://creativecommons.org/licenses/by-sa/4.0/). Imported pages retain revision links for attribution to their wiki contributors. Generated reference remains derived from the command source under the repository license.

## Check workflow examples

Run `make docs` to validate guide links and publication mappings, and `make linti` to check help size and command metadata. Runtime examples are covered by `tests/guide-examples.sh`, called from the existing Docker integration jobs: MySQL dump/restore in the MySQL cycle, and Xdebug, port changes and playable Fresh recordings in the general Docker job. Keep those checks aligned when editing their corresponding guides. Use a separate development context for manual checks; the full CI scripts create and destroy their test environment.

## Record a guide

Keep a [VHS](https://github.com/charmbracelet/vhs) `.tape` beside its guide, with the same basename (for example `guides/tools/kubernetes-pod-helloworld.md` and `guides/tools/kubernetes-pod-helloworld.tape`). Keep any recording setup in a matching `.record.sh` script beside them. Commit these sources; generated media stays in the ignored `_recordings/` directory.

```sh
TOOL=your-tool ./docs/guides/tools/kubernetes-pod-helloworld.record.sh
```

Install mise and FFmpeg first; mise provides pinned VHS and ttyd versions. Toolforge SSH must work without interactive prompts. If VHS stalls before typing, try a different Chromium executable or launcher named `chrome` at the front of `PATH`.

This recording extracts its manifest from the guide, creates and deletes only `cli-guide-hello`, and forwards localhost port 18080. It refuses to start if that pod exists. After an interrupted recording, stop its port forward and remove only the demo pod before retrying.

For Commons, upload the generated WebM using `A Wikimedia CLI - Guide - <guide-path-with-hyphens> - <language>.webm`, for example `A Wikimedia CLI - Guide - tools-kubernetes-pod-helloworld - en.webm`. Include the source guide/tape, Git revision, recording date and free license in its description. Mark recordings intended for updates with `{{Current}}`; minor corrections can replace the file, while substantially different demonstrations should use a new dated filename, following [Commons’ overwrite guidance](https://commons.wikimedia.org/wiki/Commons:Overwriting_existing_files).
