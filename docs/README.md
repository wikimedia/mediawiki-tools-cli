# Documentation publishing

[Read the guides](index.md). Markdown guides live in `guides/`, grouped by command area (for example `guides/dev/` and `guides/gitlab/`); `wiki.json` maps each source to its MediaWiki.org title. The command reference comes from Cobra help. Both are built from the release checkout and published together after a release. Existing `Cli/` URLs remain stable during the rebrand; the reference index follows the default executable name.

## Build and review

Install [mise](https://mise.jdx.dev/getting-started.html) and Go, then run:

```sh
mise trust
mise install
make docs
make docs-check
make docs-audit
```

Pandoc is pinned in `mise.toml`. The Make targets use `mise exec`, so shell activation is optional.

`_docs/` contains Markdown, converted wikitext and `pages.json`. `docs-check` reads every managed wiki page and finds its last automatic publication. It reports just the changes made on the wiki since that revision, such as spelling fixes; new release changes are kept out of these diffs. Identical reverts do not count as content changes. For guides not automatically published yet, the imported/reviewed revision is the baseline.

`_docs/wiki/report.md` lists these wiki edits with small `.wiki.diff` files and links to the exact wiki revision comparison. `publish-report.md` separately shows the full proposed release changes in `.publish.diff` files. The directory also contains downloaded content and revision snapshots; it is regenerated by each check. CI keeps it as a documentation job artifact. Checking does not need credentials or edit the wiki.

Published pages carry a content fingerprint. If someone edits a page on the wiki, the next publish stops before making any edits. For the initial migration, only reference content verified against the known legacy bot’s publication is adopted automatically (including identical human reverts); imported guides have explicit revision/content baselines in `wiki.json`.

## Review and publish selected pages

```sh
make docs-review
```

This generates documentation from your current checkout, reads the managed pages
and their publication history from MediaWiki.org, then prints the URL of a local
review interface. Open that URL in your browser. No wiki edits happen when opening or refreshing a review.
The server listens only on a random loopback port. Keep the printed URL private;
it grants access to this review session. Press Ctrl+C to stop it.

Search by title or source, filter changed/new/conflicted pages, and select pages
individually or by command family or guide area. Selection applies to visible
pages, so you can narrow an area before selecting it. Version-only updates have
a separate filter to keep them out of content reviews. Existing pages can also
be filtered to additions only, removals only, or both; unchanged pages have their
own filter. These groups count wikitext line changes, excluding version notices
and publication fingerprints. Rewriting a line counts as both an addition and
a removal. New pages remain a separate group.

Each page has four views:

- **Publication diff:** the current wiki text compared with the exact proposed
  wikitext, including a version notice if enabled.
- **Rendered preview:** proposed or current content rendered through MediaWiki.org's
  read-only parse API. Content styles are loaded from the wiki; site navigation is
  omitted. Previewing sends the proposed text to MediaWiki.org but does not save it.
- **Wiki corrections:** changes since the last publication or reviewed import.
- **Source:** the generated Markdown and its repository source location. Edit the
  original guide or command help, then refresh to rebuild and review it.

Published wikitext uses internal links for pages on the configured wiki. Links between command reference pages keep their existing relative form, such as `[[../mw_config|mw config]]`. Generated Markdown keeps full URLs for standalone use; links to other sites and URLs with query parameters remain external links.

The `mw_docker*` → `mw_dev*` reference rename is published as native wiki page
moves when the old page exists and the new title is free. Both `docs-publish`
(including release CI) and interactive publishing preserve the old history and
leave redirects before updating the content. No manual move is needed first.
The publisher account's bot password needs permission to move pages.

Use **Page moves and redirects** to inspect these pairs. The new title's diff
compares the old page content with the proposal. Selecting either title includes
both in the confirmation. Wiki corrections at the old title must be reviewed;
occupied destinations block the move and cannot be overridden by accepting a
revision. Pages already moved manually are kept in place, and equivalent
redirects are left unchanged. If publishing stops after a move, refresh or rerun
to review the preserved content and finish the update.

For a page needing review, incorporate wiki corrections into the source or
resolve the differences deliberately. **Mark wiki revision reviewed** records
that exact revision in `docs/wiki.json`, equivalent to `docs-accept`; it does not
edit the wiki. Include this change in your commit. Translations cannot be accepted
or published through this interface.

Without credentials the interface supports selection, diffs and previews. To
publish, start it with `DOCS_UPDATE_USER` and `DOCS_UPDATE_PASS` already set in your
environment. **Review selection** shows the exact page list and version, including
warnings about links to new managed pages outside the selection. Confirm
**Publish selected pages** to publish only those pages. Unselected conflicts do
not block the selection.

The server keeps the proposed content in memory: publication sends exactly what
was reviewed, even if local files subsequently change. It rechecks selected wiki
revisions before any edits and uses revision guards on every edit. A changed wiki
page blocks publication until refreshed. After an edit attempt, refresh to inspect
completed edits before another publication; a network error can leave a partial
publication. Refresh also rebuilds local sources and replaces the review snapshot.

### Documentation version labels

`DOCS_VERSION` overrides the version; `make VERSION=vX.Y.Z ...` still supplies a
release version for CI. Otherwise the generator uses a CI tag or exact Git tag,
then the current branch. Non-release checkouts display a label such as
`main / unreleased · abc1234`; local changes add `modified`. The former automatic
`latest` label now triggers this detection instead of implying a release.

The version is shown in the review interface and publication summaries. Published
pages omit version notices by default, so documentation can be reviewed and
published ahead of a release without rewriting unchanged pages when the release
is tagged. Pages stay managed: future source changes are still published, and
wiki corrections still require review. Commit source edits and reviewed wiki
baselines before the release so CI builds the same content.

To include visible version notices explicitly, use:

```sh
make docs-review DOCS_VERSION_NOTICE=1
```

With notices enabled, unreleased pages explain that the installed release may
differ. Use the same setting for subsequent publications; changing the setting
adds or removes the notice. Redirects remain plain redirects. Version notices
are excluded when importing wiki text back into Markdown guides.

## Find pages left behind

`make docs-audit` lists existing `Cli/` subpages absent from the current build in `_docs/wiki/audit.md`. It separates retirement candidates (`OBSOLETE`, or `OBSOLETE-EDITED` when corrected on the wiki) from retained translations, supported aliases, hidden commands and community pages. Review obsolete pages for redirects, adoption or manual retirement; an absent mapping is not permission to delete a community page.

Moving a Markdown file and updating its `source` in `wiki.json` preserves the wiki URL. Changing a mapped `title` creates or updates the new page; publishing never moves or deletes the old page. Keep useful old URLs as explicitly managed redirects, as the `docker` command reference does, or handle the wiki move manually after reviewing history and incoming links. The audit is read-only and needs no credentials. The `Cli` homepage and its translations remain wiki-managed: edit the Translate source page to update their branding, preserving translation unit markers.

## Bring wiki corrections into Git

```sh
make docs-pull
```

This saves Markdown proposals for guides alongside the wikitext and diffs. It does not modify tracked sources. Merge relevant guide corrections into `docs/`, or update the command help for reference corrections. Check the conversion: wiki templates and other wiki-specific markup may need manual adjustment.

After reviewing a flagged page, acknowledge the exact downloaded content:

```sh
make docs-accept page="Cli/ref/mw_docker"
```

Commit the source fixes and updated `wiki.json`. Acceptance is tied to that snapshot; a later wiki edit is flagged again. Re-run `make docs-check` before tagging a release.

## Write command help and guides

[Writing command help and guides](writing.md) describes what belongs in each.
Keep command behavior and operation in command help; use guides for workflows
and worked explorations. Help length suggestions are prompts to review clarity,
not word limits.

## Add or import a guide

For a new guide, add Markdown under `guides/`, a `source`/`title` entry in `wiki.json`, and a link in `index.md`. Relative Markdown links between mapped guides are converted to wiki URLs. Broken guide links fail the build. Mapped guides are also bundled for offline reading under `mw help guides`, following their folder paths; `index.md` provides the parent topic. Use `--web` to open the mapped wiki page. Keep command details in help and link to guides for workflows and worked examples.

To adopt an existing wiki page:

```sh
make docs-import page="Cli/guide/Gitlab" file="guides/gitlab/index.md"
```

This imports the current revision into Markdown, adds its mapping and records its baseline and attribution. Importing over an existing source saves a `.bak` copy first. Review the conversion and commit the imported files. Unmapped community pages are never published, deleted or renamed by this tool.

## Publish

Set `DOCS_UPDATE_USER` and `DOCS_UPDATE_PASS` to the wiki publishing account and bot password, then run:

```sh
make VERSION=vX.Y.Z docs-publish
```

The release job uses the existing CI secrets. To publish between releases, push the reviewed changes to `main`, open its pipeline and click **Play** on the manual `docs-publish` job. You can also start a new pipeline for `main` from **Build → Pipelines → New pipeline**. This publishes the selected commit's documentation using the same credentials and review checks, independently of the binary release jobs.

Credentials are read from the environment. Publishing repeats the drift check and sends the inspected revision ID with every edit; a concurrent wiki edit, deletion or creation causes an API conflict instead of an overwrite. There is no force-publish bypass. A conflict during publishing can leave earlier pages updated; correct it and rerun to finish.

The guides are available under [CC BY-SA 4.0](https://creativecommons.org/licenses/by-sa/4.0/). Imported pages retain revision links for attribution to their wiki contributors. Generated reference remains derived from the command source under the repository license.

## Check workflow examples

Run `make docs` to validate guide links and publication mappings, and `make linti` to check help size and command metadata. Runtime examples are covered by `tests/guide-examples.sh`, called from the existing Docker integration jobs: MySQL dump/restore in the MySQL cycle, and Xdebug, port changes and playable Fresh recordings in the general Docker job. Keep those checks aligned when editing their corresponding guides. Use a separate development context for manual checks; the full CI scripts create and destroy their test environment.

## Record a guide

Keep a [VHS](https://github.com/charmbracelet/vhs) `.tape` beside its guide, with the same basename (for example `guides/tools/kubernetes-pod-helloworld.md` and `guides/tools/kubernetes-pod-helloworld.tape`). Keep any recording setup in a matching `.record.sh` script beside them. Commit these sources; generated media stays in the ignored `_recordings/` directory.

```sh
TOOL=your-tool ./docs/guides/tools/kubernetes-pod-helloworld.record.sh
```

Install mise and FFmpeg first; mise provides pinned VHS and ttyd versions. Toolforge SSH must work without interactive prompts. If VHS stalls before typing, try a different Chromium executable or launcher named `chrome` at the front of `PATH`.

Keep recording-only setup inside `Hide`/`Show`. Select a disposable context by setting `CONTEXT` in the hidden shell setup, rather than adding recording context flags to visible commands. The recording scripts clean shell harness lines from VHS text exports with `tools/clean-recording-text.py`; run it manually for recordings made directly with VHS.

This recording extracts its manifest from the guide, creates and deletes only `cli-guide-hello`, and forwards localhost port 18080. It refuses to start if that pod exists. After an interrupted recording, stop its port forward and remove only the demo pod before retrying.

For Commons, upload the generated WebM using `A Wikimedia CLI - Guide - <guide-path-with-hyphens> - <language>.webm`, for example `A Wikimedia CLI - Guide - tools-kubernetes-pod-helloworld - en.webm`. Include the source guide/tape, Git revision, recording date and free license in its description. Mark recordings intended for updates with `{{Current}}`; minor corrections can replace the file, while substantially different demonstrations should use a new dated filename, following [Commons’ overwrite guidance](https://commons.wikimedia.org/wiki/Commons:Overwriting_existing_files).

## Record local development workflows

The local development recordings use a running Docker Compose environment and need no Wikimedia account:

```sh
CONTEXT=recording-setup ./docs/guides/dev/fresh.record.sh
CONTEXT=recording-setup ./docs/guides/dev/api.record.sh
CONTEXT=recording-setup ./docs/guides/dev/mysql-dumps.record.sh
./docs/guides/analytics/pageviews.record.sh
./docs/guides/gitlab/artifacts.record.sh
./docs/guides/updating.record.sh
CONTEXT=recording-setup-final ./docs/guides/dev/lifecycle.record.sh
CONTEXT=recording-clean ./docs/guides/dev/extension-workflow.record.sh
CONTEXT=recording-setup-final ./docs/guides/dev/tunnel.record.sh
```

The Fresh recording also requires `mw dev --context recording-setup mediawiki fresh npm ci` first. To record the initial setup flow, point it at a disposable MediaWiki checkout; the script creates a fresh context, installs the wiki and leaves its services running:

```sh
MEDIAWIKI_CODE=/path/to/disposable-mediawiki CONTEXT=recording-setup \
  ./docs/guides/dev/setup.record.sh
```

The setup script refuses to reuse a context that already has Docker containers or volumes, so choose a new context for each fresh setup. All generated media and the temporary database dump go in the ignored repository-root `_recordings/` directory.

The extension workflow recording needs an installed disposable wiki checkout without Cite already cloned or enabled; set `CONTEXT` to that context. The tunnel recording starts a temporary authenticated Cloudflare Quick Tunnel and stops it on exit, including when recording fails.
